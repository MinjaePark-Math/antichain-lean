# Extending the formalization

1. Read `formalization/GAPS.md`, `ROADMAP.md`, `PROOF_GUIDE.md` and the current complete Lean types. Identify a new mathematical result, a stronger statement or a concrete defect. The final source-facing APIs are in `DirectSourceEndpoints` and `RankLimitsSharp`.
2. Add a proof module and import it in `Antichain.lean`. Keep the pinned versions unless upgrading them is an explicit change.
3. Run `python verify.py` for fresh compilation and the exact two-worker audit, or add `--audit-jobs 1` for lower aggregate memory use. Review every new statement and its transitive axioms. Keep zero-probability cases, dimension restrictions, floor measure and asymmetric costs explicit. Final paper certificates must discharge geometric records and concentration inputs internally.
4. Update both statement and proof-method correspondence. Preserve stable IDs when editing an existing assertion, and assign new IDs for genuinely new assertions. Numbering is presentation and may change. Review the [proof-correspondence ledger](formalization/proof-correspondence.json) and [revision review](formalization/REVISION_REVIEW.md); agreement of theorem statements does not certify a particular written argument.
5. Refresh `formalization/coverage.json`, the paper's status annotations and the frozen release files only after checking the new source and complete types. Retain the original written proofs in `source/`. For a different Lean proof route, supply a complete readable proof with exact Lean references in the appropriate `formalization/human-proofs-*.tex` fragment and link its appendix label from the method ledger. The generated companion may remove editorial color wrappers, but must preserve their contents.
6. Rebuild with `python scripts/build_paper.py`, then run `python scripts/record_paper_numbering.py` (requires `pypdf`) and visually inspect the paper. The numbering record must match actual current PDF headings and auxiliary labels; old page counts or PDF hashes are rejected. The build receipt binds every local paper input and the PDF. Run `python scripts/check_release.py` against the deliberately refreshed snapshot.

In the authoring workspace, run `python scripts/prepare_release.py --draft-only`, then `python scripts/build_paper.py` and `python scripts/record_paper_numbering.py`, inspect the output, and finally run `python scripts/prepare_release.py` to regenerate this public folder from the reviewed original, checked Lean project and matching PDF. Within a downloaded public repository, the Lean and TeX files remain directly editable; frozen snapshot updates are deliberate release edits, not hidden checker behavior.

For a manuscript-only revision, a new kernel run is unnecessary only if every checked Lean source and audit input still matches the saved complete evidence exactly. Renew the statement and proof-method reviews, source fingerprints, appendix and PDF receipt, and record explicitly that the kernel evidence is reused. Any Lean or audit-input change requires step 3 again. The current revision reorganizes the claims and changes several proof routes. Its Lean changes require a fresh audit.
